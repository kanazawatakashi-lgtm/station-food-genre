# 集計方法の整理（亀戸の試作から）

2026-10-02。亀戸駅で試した各手順の「手間」と「効果」を比べ、多くの駅に広げるときのやり方を決めるためのメモ。

## 亀戸で試した手順の費用対効果

| 手順 | 何をしたか | 効果（亀戸） | 手間 | 判断 |
|---|---|---|---|---|
| Overture 抽出 | S3 の GeoParquet を範囲指定で読む | 飲食 910 件。土台 | 小。23区全体（約14万件）でも1分程度 | **主データにする** |
| 店名ルール＋Overture 細分類 | 正規表現（チェーン名含む）と細分類の対応表 | 判定率 81.8%（23区では 73.4%） | 小。一瞬で終わる。ルールは使い回せる | **主手段にする** |
| Claude の店名判定 | 決まらない店を店名・分類・住所から判定 | +53 件（約6%）。高・中のみ採用 | 小。API で一括処理できる | **使う**（比較対象側にも同じく掛ける） |
| 重複の除去 | 50m 以内・店名一致・同ジャンル | 約1%減 | 小 | **使う**（安いので） |
| OSM のタグ | Overpass で取り、店名と距離で照合 | 判定不能を埋めたのは +5 件だけ | 中。ローカル実行が必要 | **補完には使わない。精度確認に使う**（一致率 89%） |
| JFF（OpenPOI 経由） | bbox 分割で取り、名寄せ | +95 店（約10%） | 大。ローカル実行、名寄せの調整、飲食店以外の除外 | **主集計には入れない**（下記の理由） |
| 商用 API（ホットペッパー、Yahoo、ぐるなび、Google） | — | — | — | **使わない**。規約で保存・二次利用が制限されている。ぐるなびは無料提供終了 |

## 分かったこと

1. **ジャンル判定の精度はおよそ9割。** 店名ルールの結果は、Overture 細分類との一致が 88%、OSM のタグとの一致が 89%（それぞれ独立に確認）
2. **店の網羅に穴がある。** OSM にあって Overture に無い店が、OSM の店の2割前後ある。漏れはラーメン店・居酒屋に多い
3. **JFF は穴を埋めきれず、地域でむらがある。** 江東区は区の許可一覧が入っているが、墨田区は国の電子申請分だけ。
   亀戸 1km 圏でも JFF の飲食店は約250件で、OSM にしかない店35件のうち JFF で拾えたのは2件。
   JFF を駅ごとに足すと、**区によって足される量が違うので駅どうしの比較がゆがむ**
4. **比較はデータの作り方をそろえることが一番大事。** 駅側だけに追加データや追加の判定を入れると、構成比の差が
   「街の違い」なのか「データの違い」なのか分からなくなる。Overture の漏れも、全駅で同じように漏れるなら比較への
   影響は小さい
5. **居酒屋とバーの境界は分類方法で動く。** 酒場系（居酒屋＋バー＋スナック）をまとめると亀戸の LQ は 1.04 で
   平均並みだが、内訳は 1.59 と 0.79 に割れる。内訳は比べず、まとめて扱うのが安全
6. **件数の少ないジャンルは LQ が不安定。** 1駅10件未満のジャンルは1〜2店で LQ が大きく動く

## 多くの駅に広げるときのやり方

**方針: 「都内全域を一度に処理し、駅ごとに切り出す」。駅ごとに取得・判定しない。**

```
1. Overture: 東京都全域の飲食 POI を1回で取得             （クラウドで可）
2. 全件を一度に判定: 店名ルール → Overture 細分類
3. 決まらない店名だけを重複なしで Claude API に一括で送る     （Batch API で半額）
4. 重複の除去を全域で1回
5. 駅一覧: 国土数値情報 S12（座標・乗降客数）。同名駅は事業者をまたいで合算  （取得だけローカル）
6. 駅ごとに半径1km の店を切り出す（重なりは両方に数える）
7. 比較対象（都全域または23区）の構成比も同じ表から出す → 特化係数（LQ）、乗降客1万人あたり店舗数
8. 精度確認: いくつかの駅だけ OSM と照合し、一致率と漏れ率を記録                （取得だけローカル）
```

この形にする理由:

- **判定が1回で済む。** 駅の圏は重なるので、駅ごとに判定すると同じ店を何度も判定することになる
- **比較対象と駅側の判定方法が自動的にそろう。** 今の亀戸では Claude 判定を比較対象側に掛けられず、LQ をルールだけで
  計算していた。全域を一度に判定すれば、Claude 判定も含めた結果で LQ を出せる
- **Claude に送る量が減る。** チェーン店や同名店は1回の判定で済む。23区の判定不能は約3.7万件。店名の重複を除けば
  さらに減る。費用は Batch API で数十ドル程度の見込み（モデルと件数で変わる。実行前に件数で見積もる）
- **ローカルでの作業が S12 の取得（と精度確認用の OSM）だけになる。** Overture はクラウド環境から取れる

## 表の出し方

- ジャンルは今の37区分で判定し、**集計表では件数の少ないものをまとめる**（例: 酒場系＝居酒屋＋バー＋スナック・パブ、
  各国料理をまとめる など）。まとめ方は全駅の件数分布を見てから決める
- 各駅の表には **判定率と、判定不能の件数** を必ず載せる
- LQ は **件数10件以上のジャンルだけ** 示し、それ以外は「件数少」とする
- 「Overture は店の約2割を取りこぼしている（OSM との照合での目安）」ことを注記する。ラーメン店・居酒屋は少なめに出ている

## JFF の扱い

主集計には入れない。使うとしたら次のどちらか。

- **区の許可一覧が入っている区だけで、補正の大きさを見る**（江東区など）。全駅の比較には使わない
- 都が全区分の営業許可データをまとめて公開していないか確認し、そろっているなら主データに加える（未確認）

## まだ決めていないこと

- 対象駅を絞る乗降客数の閾値
- 比較対象を23区にするか都全域にするか（多摩地域の駅を入れるなら都全域）
- 集計表でのジャンルのまとめ方
- 出力の形（スプレッドシート、ダッシュボードなど）

## 進み具合（23区全域、2026-10-02）

比較対象は23区に決定。乗降客数の閾値は駅の切り出し（手順6）まで不要なので後で決める。

| 手順 | 状態 |
|---|---|
| 1. Overture 取得 | 済。`scripts/fetch_overture_area.py tokyo23`。Overture divisions の23区境界で切り出し、区名付きで 122,467 件 |
| 2. ルール判定と重複除去 | 済。`scripts/classify_area.py tokyo23`（6秒）。重複をまとめて 119,825 件、判定率 75.0% |
| 3. Claude 判定 | モデル選びの試験を準備（`scripts/compare_models.py`、Opus 5.5 と Haiku 4.5 を600店で比較。ローカルで実行）。本番のスクリプト済（`scripts/classify_area_with_claude.py`）。判定不能 30,008 件・店名 28,444 種類を 285 リクエストで送る。**ローカルで実行**（API キーが必要） |
| 4. 駅の切り出し | 未。S12 の取得が必要 |

- 手順2でチェーンの英字表記（Gyu-Kaku、Jojoen、Denny's など）、町そばの屋号（長寿庵、更科、砂場 など）、
  Overture の未対応分類（dim_sum、bagel_shop、gastropub など）をルールに足し、判定率を 73.0% → 75.0% に上げた
- 判定不能の店名はほとんどが1店だけの名前（32,306 店で 30,238 種類）なので、ルールでこれ以上大きくは減らない
- 手順3の費用の目安: 送る本文は約190万文字。Opus 5.5 を Batch API（半額）で使うと 20ドル前後、Haiku 4.5 なら
  5ドル前後の見込み（出力の長さと思考の量で上下する。正確には実行後の usage で確認する）
