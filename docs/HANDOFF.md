# 駅圏 飲食ジャンル過不足分析 — 引き継ぎメモ

claude.ai での相談（2026-10-02）を Claude Code に引き継ぐためのまとめ。まだ何も実装していない。

## 目的

都内の駅（一定の乗降客数以上）の半径 X km 圏にある飲食店を、ジャンル別（ラーメン、すし、カフェ…）に集計して駅ごとの比較表を作る。
狙いは、**各駅経済圏でジャンル別の過不足を可視化すること**。

## 決定済みの条件

| 項目 | 値 |
|---|---|
| 半径 | 1km |
| 圏の重なり | 重複して数える（隣の駅と重なる店は両方の駅に入る） |
| ジャンルの細かさ | できるだけ細かく |
| 試作の対象駅 | JR 亀戸駅（1駅で試し、精度を確認してから広げる） |

## 未決定

- 対象駅を絞る乗降客数の閾値（全駅へ広げるときに決める）
- 最終的なジャンル体系（試作の結果を見て決める）
- 出力形式（スプレッドシート／ダッシュボードなど）

## データソース

### 1. OpenPOI API（店舗の網羅用）

- 仕様書: https://docs.openpoiapi.com/
- OpenAPI 定義: https://api.openpoiapi.com/openapi.json
- ベース URL は `https://api.openpoiapi.com`。認証なし、CORS は全オリジン許可。
- 日本全国の POI 約337万件を収録。内訳は Overture Maps 約249万件と、食品営業許可・届出オープンデータ（Japan Food Facilities, JFF）約88万件。
- `GET /v1/search` のパラメータ
  - `q`：キーワード。複数語は OR 検索。
  - `center=lng,lat`、`radius`（m）
  - `bbox=minLng,minLat,maxLng,maxLat`：`center` より優先される。
  - `limit`：最大 200。
- レート上限は API 全体で 200 req/s（バースト 600）。超えると 429。
- 主なレスポンス項目: `name`, `name_kana`, `address`, `category`, `lat`, `lng`, `level`（位置精度。8=街区・地番）, `source`（`jff` / `overture`）, `licenses`, `attributions`
- MCP サーバーもある: `claude mcp add --transport http japan-facilities https://api.openpoiapi.com/mcp`

**確認済みの制約**（新宿駅西口で実測）

- **1回 200 件の上限があり、ページ送りはない。** 500m×400m の bbox で上限の 200 件に達し、結果は名前順で切られていた。全件を取るには、bbox を 200 件未満になるまで再帰的に4分割する必要がある。
- **`category` は粗い。** `restaurant` / `cafe` / `bar_izakaya` / `bakery` / `unknown` などしかなく、ラーメン・すしの区別はない。全体の約55%は `unknown`。
- **JFF は「許可1件＝1レコード」。** 同じ店が業種違いで複数レコードになることがある。

### 2. Overture Maps Places 元データ（細かいジャンル分類用・最有力）

- OpenPOI は Overture の細かいカテゴリを粗くまとめて配信している。元データには `ramen_restaurant`、`sushi_restaurant`、`izakaya` などの細分類がある。
- 無料公開の GeoParquet。DuckDB で bbox を指定して直接クエリできる。
  - パス例: `s3://overturemaps-us-west-2/release/<release>/theme=places/type=place/*.parquet`（OpenPOI が現在使っているリリースは `2026-08-19.0`）
  - **カテゴリ列のスキーマ名はリリースで変わっている**（`categories.primary`、`basic_category` など）。最新版のドキュメントで確認すること: https://docs.overturemaps.org/
- 弱点: JFF 由来の店には分類がない。

### 3. 駅データ

- 国土数値情報「駅別乗降客数データ（S12）」を使う。駅の座標と乗降客数が入っている。
- 同じ駅名で事業者が別（JR／メトロ／私鉄）の場合は合算する。
- 亀戸駅の座標は概算で lat 35.6974, lng 139.8268。S12 か地図で確認すること。

## ジャンル判定の方針

1. **Overture の細分類を使う。** Overture 由来の店はこれでジャンルが付く。
2. **店名から判定する。** Overture に分類がない店と JFF 由来の店が対象。
   - キーワード（麺屋・中華そば・鮨・寿司・焼肉・ホルモンなど）
   - チェーン辞書（一蘭→ラーメン、日高屋→中華、サイゼリヤ→イタリアン、スタバ→カフェなど）
   - それでも残った店は、Claude が店名を読んで判定する（1駅あたり数百〜千件程度なので現実的）。
3. **判定できない店は「その他飲食」にする。** 駅ごとの判定率も出力し、精度が見えるようにする。
4. **Overture と JFF の名寄せをする。** 座標が近く名前が似ている店を同一とみなして重複を除く。名寄せの精度が誤差の主な原因になる。

その他の選択肢（今回は不採用）

- ホットペッパーグルメ API：無料・要登録。ジャンルは十数種類と中程度。掲載店のみ。
- Google Places API：有料。分類は細かいが規約上の制限がある。

## 過不足の指標

店の件数だけで比べると、大きい駅ほど何でも多く見えてしまう。次の2つで比べる。

- **特化係数（LQ）**：その駅のジャンル構成比 ÷ 比較対象全体の構成比。1未満なら相対的に不足。
  - 1駅だけの試作では、比較対象（例：東京都全体や他の数駅）を別に用意する必要がある。
- **乗降客1万人あたり店舗数**

## 注意点

- このデータは絶対数より、構成比の相対比較に向いている。
- 閉店済みの店が残っていることがある。JFF は毎週更新、Overture は数ヶ月遅れのこともある。
- 出典表示が必要。保存するときは `licenses` / `attributions` もレコードと一緒に残すこと。

## 環境メモ

claude.ai のクラウド作業環境からは、`api.openpoiapi.com` と Overture の S3 がネットワーク制限で遮断されていた。ローカル（Claude Code）なら制限はない想定。

## 最初の一歩（提案）

1. 亀戸駅の座標を確定する。
2. Overture 元データから、亀戸駅 1km 圏の飲食系 POI をカテゴリ付きで取る。
3. OpenPOI API から同じ圏を bbox 分割で全件取り、JFF 分を補完して名寄せする。
4. ジャンルを判定し、判定率を確認する。
5. 亀戸駅のジャンル別件数・構成比の表を作る。比較対象を決めて特化係数も出す。
